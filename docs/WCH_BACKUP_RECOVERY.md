# WCH verification and closed-case backup/recovery

16 October 2026. Continues the [firmware investigation](FIRMWARE_MODEL_FOLLOWUP.md).

**We cannot currently back up and independently recover this dongle with the
case closed.** The older WCH comparison method has credible evidence, but its
prerequisites are unconfirmed here. Later loaders block that method. No USB
commands, loader entry, reset, erase, write or electrical experiment occurred.
The installed application, calibration and native rollback remain unchanged.
This is an evidence boundary, not proof that every future route is impossible.

## Verification is an oracle, not a direct read

The [original 2019 reports](https://www.mikrocontroller.net/topic/462538?page=single)
describe reconstructing memory through match/mismatch comparisons without
installing a dumper. With a known suffix, shifting the comparison window backward
one byte leaves one unknown byte to guess. Success depends on loader revision,
session encoding, memory boundaries and independently reaching that loader.

The [combined 2.31/2.40 reconstruction](https://www.mikrocontroller.net/attachment/471025/bootloaderV24.asm)
was downloaded as data and inspected. Its 2.31 variant permits unaligned starts;
2.40 requires eight-byte alignment, rejects starts at or above `0x3800`, and
latches the first comparison mismatch. Explicit latch clears occur at main
initialization and code-erase completion, not ordinary USB bus reset. The
separately inspected [2.50 reconstruction](https://www.mikrocontroller.net/attachment/570882/bootloaderV25.a51)
retains the alignment/start/latch checks. These are generic reconstructed loaders,
not Nanoleaf source. The author's binary-equivalence claim was not rebuilt here.

The guard checks only the start: a 56-byte comparison from `0x37f8` can extend
through `0x382f`. That alone supplies neither arbitrary-byte readback nor a full
loader dump. Malformed-input behaviour and hypothetical bypasses remain
unverified; none was tested on the dongle.

## Later evidence changes the assessment

The [2020 follow-up](https://www.mikrocontroller.net/topic/462538?page=3#6390409)
explains the alignment and sticky-error changes. Its newer-loader dump used an
installed fake loader/dumper, which changes flash and cannot preserve an unknown
stock application. In November 2024 the author mentioned an unfinished possible
approach. Their [22 August 2025 update](https://www.mikrocontroller.net/topic/462538?page=4#7926922)
withdraws that optimism: they no longer believed firmware dumping was possible
on 2.4/2.5. This assessment supersedes treating the older speculation as a ready
method; it does not prove universal impossibility.

[isp55e0](https://github.com/frank-zago/isp55e0/blob/master/README.md) likewise
documents failed verification poisoning subsequent comparisons until a power
cycle. Its data-flash dump is not a complete code backup. The pinned
[chflasher source](https://github.com/atc1441/chflasher/blob/e9021204c97a7a74d30004d8673369bc17a02a99/chflasher.py)
normally erases, writes and then verifies. It is not a backup probe. No generic
flasher was compiled, imported or run.

## Independent offline check

The [new model and nine controls](../perf/loader-backup-2026-10-16/README.md) use
generated memory only. There is no device adapter, firmware-file input, packet
encoder, loader-entry path or write/erase implementation. The older model
reconstructs 64 generated bytes in 9,268 comparisons; the newer alignment rule
stops that walk. Other controls cover sticky mismatch, incorrect known suffix,
range crossing, bounded inputs and unchanged memory.

Those are deterministic synthetic counts, not USB measurements or dongle
verification. An unconstrained aligned eight-byte equality guess has `256^8`
possibilities; the one-unknown-byte argument no longer applies. Starting a new
model clears its simulated latch, which proves no convenient real-device
restart/entry route. This is selected semantic modelling, not instruction-level
emulation, formal proof or complete malformed-input validation.

## Closed-case entry remains a separate barrier

The manufacturer-authored [CH552 datasheet](https://cdn-learn.adafruit.com/assets/assets/000/129/847/original/CH552DS1.PDF)
describes a flash-resident loader and configurable power-on entry, rather than
immutable USB ROM rescue. USB D+ shares P3.6; generic loader options select
between a data-line condition and another GPIO. An external USB fixture is
therefore a conditional closed-case possibility only. Chip, retained loader,
options and electrical path remain unknown. No fixture was built or attached.
Generic resistor recipes are not instructions for this unit: USB pins use the
V33 domain. No protection or option bits were queried or changed.

Nanoleaf's HID loader might replace WCH's factory loader or coexist with it;
no memory map establishes either. Confirming CH552 alone would not establish
WCH ISP availability. A command handled by working application code is not an
independent route after that code fails. An inaccessible GPIO could also make
factory entry incompatible with the closed-case requirement.

| Required capability | Evidence for this dongle |
| --- | --- |
| Exact MCU and loader layout | Unconfirmed; CH552 remains a lead |
| Entry after application damage | No demonstrated closed-case path |
| Complete code and loader backup | None; stock updates are not memory dumps |
| Factory/NVS/options preservation | Locations and read/restore contract unknown |
| Stock restore through surviving vendor loader | Updater exists; entry, compatibility and restoration untested |
| Recovery after loader damage | No closed-case route established |
| User calibration and native rollback | Preserved; separate from MCU backup |

## Vendor source and updater findings

All ten public protocol revisions were inspected with their returned version
numbers checked. Revisions 1–3 link `nanoleaf/ch552_testing/src/main/hid_debug.py`
and describe DFU; 4–10 omit that link and those DFU entries. The linked filename
is a host demo, not evidence production loader source was included. No usable
production source, decoder/encoder or independent-entry procedure was obtained.

Fresh anonymous repository and fork lookups return 404, which cannot distinguish
private, deleted or moved content. The stock firmware bucket denies listing;
access was not bypassed. Software Heritage searches return unrelated token
matches and do not establish absence. Exact-origin/archive limits from the
previous investigation still apply. Revision hashes and lookup limits are
retained without publishing private metadata or vendor source.

The hash-pinned Desktop 3.0.1 methods were inspected again as text.
`initializeFromSerialNumber` automatically invokes updating when it finds the
expected vendor loader and obtains an image. `#J` erases before forwarding
61-byte stock records and restarting. These methods contain no code/factory-data
backup or separate read-only flash verification step. The stock desktop app is
therefore not a passive loader-identification tool. This does not prove the
controller lacks undocumented commands. Offsets and semantic findings are saved.

## Decision

The older WCH oracle is conditional research, substantially narrowed by the
2.4/2.5 restrictions and later author update. It is not a backup plan for this
unidentified retail unit. No safe hardware next step follows from these results;
loader entry remains unauthorized.

Useful progress requires evidence of the actual boot chain, supported closed-case
entry and factory preservation, or a validated decoder together with an
independently established restoration route. Public source/archive research can
continue without operating the device. No destructive workaround is justified.
